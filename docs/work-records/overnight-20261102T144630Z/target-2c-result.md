## Follow-up recovery and coordination repair

Follow-up commit `b6da73c115a0cbb850b92f6fa158e4bf87d34f10`, parent `c6a6f5298a424352d32be5237156f99937d16461`. The checkout was clean after committing. This supersedes the earlier statements that claim push recovery, hook/index cleanup, stack binding, target-plan lease contention, new checkout coordination, and the exported old start bypass are unimplemented or untested.

A failed claim commit restores the file only if it still contains the invocation's edit and resets the plan index entry only if it contains that exact edit, preserving unrelated state. A retry recognizes a tip claim only when its subject/trailers, sole changed path, file mode, ready parent and exact status-only edit match, then retries required publication before binding. A failed branch update reports an orphan commit separately from a binding already reachable on the branch. `flows.startPlan` delegates to the same prepared first-start implementation. `--run` directs users to an installed extension; human and JSON outputs report provenance and `nextCommand: null`.

Worktree setup now releases the first complete lease set, then acquires a new complete ordered set that includes the registered checkout; it rechecks the captured target, dependency and plan refs against their expected post-claim/binding values both before release and after acquisition. It also validates the checkout branch, HEAD, and tracked, untracked and ignored status. Contention or changed refs/checkout leaves the new checkout intact for inspection and does not invoke or clean up a hook. This is a release/reacquire protocol, not an upgrade. A dependency or target plan first discovered during fetch refuses for retry so its plan lease can be included.
