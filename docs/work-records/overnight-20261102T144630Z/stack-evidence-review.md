## Finding: a done declaration can cause dependency changes to disappear from a stacked child

`packages/cli/src/plan/flows.ts:282-284` accepts every dependency whose target record says `done`. At lines 309-321 finish reads the stack marker and validates target compatibility, then at lines 358-363 rebases the child onto the target using the recorded stack base as upstream. This happens before the human finalization challenge at lines 380 onward. The corresponding explicit restack path at lines 769-780 assigns `merged` solely from target `status === "done"`; lines 792-810 replay only commits after the stored upstream and write an unstack marker. Neither checks that the dependency work excluded by the upstream was integrated into the target. `mergedStackBase` at line 99 also calls such a declaration merged in its notice; that is a misleading report, independently of the rewrite.

This is distinct from whether a user may manually declare done. `docs/specifications/features/plan-status.md:254` says a stored done declaration alone does not prove integration and managed operations refuse unsafe or ambiguous mutation. `docs/specifications/architecture/reference-cli.md:407` requires completed dependency work and its terminal record on the selected target; lines 411-413 state manual declarations do not skip evidence checks. Feature plan-execution lines 239-250 say unstacking onto the target is triggered when the base *merges*. A record of intent is therefore insufficient evidence of the condition that makes dropping base commits safe.

## Smallest supported remedy and limitations

Before any stacked finish or restack rewrite, independently establish that the selected target contains the dependency work that would otherwise be excluded. If evidence is absent, ambiguous, stale or conflicts with captured refs, refuse before rebase and retain both checkouts and markers; report reconciliation is needed. Bind and recheck the exact captured target and dependency evidence under the existing leases. Apply the same distinction to dry-run/merged notices, so a declaration does not assert a merge. Add focused regression fixtures for both commands asserting unchanged child HEAD/tree/marker after manual done, alongside a proven-integration success.

Ancestry of the recorded stack-base commit in the target independently proves the particular snapshot inherited by the child is present, even when the base branch has been deleted. It does **not** prove any subsequent dependency work is integrated. When the dependency head is available, proof that its exact head is integrated in the selected target, together with the relationship of that head to the recorded stack base, can establish a stronger condition. Existing `plan/activity.ts:153-170` reports integration using exact branch-tip ancestry or trusted forge merge evidence tied to exact head and target, but it returns unverifiable without a branch, and its report is not itself a rewrite guard. This distinction matters if the base branch was subsequently rewritten, or if the completed dependency includes changes after the child's snapshot.

Legitimate squash/rebase integration does not generally preserve original ancestry; a blanket ancestry-only requirement blocks the existing `lifecycle.test.ts:183-218` squash scenario. Trusted forge evidence identifying the exact merged head and target, linked to the inherited snapshot, can support it. Local squash with no trusted external receipt, or a removed branch with insufficient surviving evidence of later completed work, can be indistinguishable from a manually copied done record; preserve history and ask for explicit reconciliation rather than infer integration from status, branch deletion, or mere content similarity. The current specifications require both support for squash/rebase and independent evidence, but do not define a durable local reconciliation/attestation protocol or specify exactly what surviving evidence must prove after branch removal. This is a contract gap; do not invent a silent override. An ancestry check of the recorded snapshot is a narrow safeguard for the demonstrated loss, not full proof that all later dependency work is complete.

## Repair review verdict

Reviewed `b3397a0ca4b18d08a8bcdc3baef2e1ba73fae18f` in `/workspace/overnight/stack-evidence`: the repair addresses the demonstrated failure. `requireStackIntegration` captures and validates a compatible dependency head, requires the recorded upstream to be its ancestor, then requires either that head to be an ancestor of the selected target or an exact-head, exact-base merged forge record with its merge commit contained in that target. Finish invokes it before any rebase; restack invokes it before an unstacking rebase, including dry-run. Existing ref rechecks follow the evidence collection. The done-only merge notice also requires evidence. A missing dependency branch results in conservative reconciliation rather than proof by absence or content equivalence.

Independently reran the original two-fixture reproduction against the repaired compiled CLI using `timeout 60s node /tmp/stack-evidence-repair-repro.cjs`, with supported escalation, no network, and automatic cleanup of the script's temporary fixtures. Both operations exited 1 with `integration ... is unverified`; each child HEAD remained unchanged, with both inherited `a.txt` and own `b.txt` present. The review also inspected the repair's focused tests: ordinary contained-head restack succeeds; the removed-branch case refuses; a scripted forge supplies exact-head/base evidence for a squash. The worker reports all 53 finish tests and all 16 lifecycle tests passing, including the focused cases; these suites were not repeated in this review. Scripted forge evidence does not constitute a live forge test. The local-squash and removed-branch evidence gap described above remains a deliberate conservative limitation.
