# Completion assessment step 2 review

Reviewed commit c88c3dd in `/workspace/overnight/completion-2` against the step 02 criteria, architecture/reference-cli completion operations, architecture/file-formats §10, feature/spec-system and feature/tooling. Read-only review; no broad test reruns. Step 03 writer work is assigned separately and not reviewed as an omission.

## Findings

1. **Known dependency removals are omitted when a recorded dependency is unavailable.** `packages/cli/src/core/completion.ts:111-122` sets `incomplete` if a recorded ID that is no longer in the current, fully traversed closure no longer resolves, and suppresses every `dependency_removed` reason when `incomplete` is set. For example, remove the root's sole `extends` reference and delete that old dependency file: the closure is known empty, but the result has `root_changed` and `dependency_unavailable` without the known `dependency_removed` mismatch. The specification requires complete membership key-set comparison and reporting all known mismatches even under `unverifiable` precedence. Distinguish uncertainty caused by an unexplored current subtree from unavailable old recorded content; emit removals whenever the current complete closure establishes them. Add a regression for a removed reference whose old target is unavailable, and one that retains a known mismatch while another dependency is unavailable.

2. **Reports may assess a different root revision from the content displayed or validated.** `packages/cli/src/commands/spec.ts:141-145,182-185`, `packages/cli/src/spec/validate.ts:236-244`, and `packages/cli/src/spec/completion.ts:6-14` repeatedly read working-tree files rather than evaluating the loaded/displayed bytes in one consistent snapshot. For example, `show --json` reads `content`, then `assessFile` reads the root again; a concurrent edit between these reads can yield a `current` assessment against bytes different from those in the same result. The snapshot resolver also reads a dependency afresh on each resolution. Capture immutable root/dependency contents and resolution inputs for each report, and use those same bytes for parsing, validation, display and assessment; exercise a controlled mutation between reads. File-formats §10 specifies the same selected checkout/revision throughout the graph, and feature/spec-system ties assessments to the inspected definition.

## Coverage observations

The new tests cover status precedence, root/hash changes, added/removed membership in a fully available graph, unsupported versions, an unavailable current dependency, invalid root metadata, and a common CLI report. They do not cover a removed/deleted recorded dependency or concurrent mutation between reads. No execution tests were run in this independent review.
