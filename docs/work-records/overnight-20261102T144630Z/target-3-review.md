# Review of target lifecycle step 3 (d061fa5)

Verdict: **changes requested**. These are read-side defects in the assigned step, not requests to implement the separately assigned finish or retarget writers. Review was static against the step 03 criteria and reference-cli contracts; I did not rerun the worker's reported 35 tests or invoke live hosts.

1. **[P1] Resolve records, dependencies and config from the selected snapshot.** `packages/cli/src/commands/plan.ts:63` parses all initial records from the invoking working tree and `:84-104` uses those records and config for stored/effective status and dependencies even after `planReport` resolves a different target. For example, a ready plan on candidate can be shown done or blocked based on an unrelated invoking branch; dirty edits can similarly affect the report. `planTextAt` (`packages/cli/src/plan/activity.ts:58`) always uses the invoking config's `plans.dir`, and no selected target/branch config is loaded or compared, so a different target path or config can make real records invisible or mix snapshots. Resolve the selected committed plan and target snapshots, their config and paths, and derive status/dependencies from the appropriate selected records; diagnose conflicting routing/path interpretations. Test a missing invoking folder, different target status/dependencies, dirty invoking records, and selected config/path differences. The reference-cli read-side contract explicitly requires context and parsing for the selected snapshot; target dependencies come from that target.

2. **[P1] Use the reconciled branch consistently for show and live activity.** `planReport` selects a remote-ahead branch (`activity.ts:78-79`), but `planShow` (`plan.ts:238-242`), discovery (`plan.ts:79`), and `getPlanActivity` (`activity.ts:230-241`) always prefer the local branch. With local an ancestor of origin, show prints stale PLAN.md while the appended provenance describes the newer remote; live steps, HANDOFF and branch-only stored status are likewise stale. An unstarted plan's activity also picks the local target even when its remote ref is ahead, or falls back to an unrelated default when the selected target is unavailable. Pass the resolved commit/selected path through every reader, and report unavailable evidence rather than reading a different target. Add local-behind-remote and target-behind-remote tests with differing plan text/steps.

3. **[P1] Refuse malformed or conflicting execution bindings, not just errors matching message text.** `activity.ts:86-93` turns most `resolvePlanContext` errors into successful reports, including `Malformed execution binding` and `Inconsistent execution target declaration or chain`; it then exposes unvalidated values as recorded context. `snapshot` at `:76` also omits the committed `target_branch` declaration, so disagreement between the declaration and execution binding is never checked. A conflicting binding must be a `PlanStateError` for list/show, while missing target refs and genuinely unavailable historical evidence can remain inspectable/unverifiable. Use typed failure categories and validate declaration and chain in each branch snapshot; test malformed binding, inconsistent target-change chain and differing declaration.

4. **[P2] Detect pending retarget relative to the checkout's committed record.** `activity.ts:119-122` compares the checkout file to the *selected* remote-ahead binding, not its own local HEAD. A clean local checkout behind a remotely retargeted branch therefore falsely reports its old target as a pending edit. Compare working content with its local branch's committed binding to identify an actual uncommitted retarget; keep the selected committed destination separate. Add clean-behind and dirty-behind cases. The retarget writer itself is step 5; this is the reader's current reporting contract.

5. **[P2] Include pending retarget and uncertainty in human list output.** `plan.ts:136` prints target, start, optional comparison and integration only; pending retarget and diagnostic/freshness are omitted. Both original step 03 criteria require list/show/live reporting of pending state and distinguishable missing/offline evidence. JSON carries these fields, but a normal human listing silently hides a pending destination or the reason context is unavailable. Display pending retarget and relevant freshness/uncertainty in the human report, and test both list modes.

Additional assessment: the patch correctly constrains open PR lookup by base and merged PR evidence by exact head/base plus merge commit ancestry. It fetches all origin heads once per live list invocation. No finding here asks for lifecycle approval, finish mutations, or retarget writes. Existing `planNext` and `mergedStackBase` attention paths remain on older resolution as the worker disclosed; insofar as they produce misleading read-side notices, update them or explicitly scope and track the remaining work during repair.

6. **[P1] Validate the target record before using it as terminal integration evidence.** `activity.ts:105-111` takes any leniently parsed `status: done` at the expected path as the target plan's terminal record without checking its `id` or schema. A different or malformed plan at that path plus branch ancestry or matching forge evidence can therefore be reported as integrated for this ID. Parse and validate target identity and record before reporting target status or claiming integration, with a conflicting identity error or explicit unverifiable evidence as appropriate. Add ancestry and exact-head forge cases with a mismatched target ID and malformed record.
