## Findings

1. **Post-commit HEAD movement can publish an unrelated commit as the lifecycle commit.** `packages/cli/src/plan/flows.ts:801-803,815-824` invokes `git commit`, then identifies the result solely by `rev-parse HEAD` and compares its tree to the expected tree. A guarded post-commit hook can create an empty child commit after the actual abandonment commit (for example, a one-shot hook running `git commit --allow-empty` with hooks disabled). The child has the same tree, so the tree check and target-ref equality pass, and the code pushes the child SHA and reports it as the abandonment commit, without checking its parent or trailers. If later cleanup fails, retry authentication sees the child's unrelated trailers and cannot resume. A failing commit/hook that moves HEAD similarly produces an unverified "Abandonment commit ... retained" message at line 806. Bind success to the actual commit created by the command and verify its expected parent, tree and lifecycle trailers before publication; if HEAD moves, preserve state and report reconciliation. Add a guarded post-commit hook regression asserting no unintended publication and an accurate recovery message. The worker's hook test covers a changed tree, not a same-tree child.

2. **Repeated abandon after completed success contradicts the terminal-state contract.** At `flows.ts:706-734`, any authenticated abandonment commit still at target HEAD enters cleanup, even after a previous invocation succeeded. `lifecycle.test.ts:65-82` explicitly asserts that a second `abandon --delete-branch` succeeds and deletes a branch retained by the first successful invocation. `architecture/reference-cli.md:459` and `features/plan-status.md:46-49` require an already abandoned plan to fail; the new test reverses the previous terminal-state assertion. The same branch handles legitimate interrupted cleanup, but a matching HEAD and trailers do not distinguish that from completed success. Preserve retry recovery using evidence of a pending operation or a separately specified recovery mechanism, while keeping successful repeated abandonment subject to the terminal refusal. This is a contract conflict, not a claim that the explicitly requested branch deletion lacked user intent.
