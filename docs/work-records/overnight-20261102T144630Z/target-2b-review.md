## Findings

1. **Wrong-source plan validation blocks valid starts/resumes** — `packages/cli/src/plan/prepare-start.ts:62-65`. The invoking HEAD plan is parsed and schema-validated unconditionally, even when `--target` already selects the source or an existing plan branch supplies the execution binding. A malformed or duplicate unrelated invoking-checkout record therefore prevents start/resume despite a valid target and plan branch. Read a discovery hint only when it can affect first-start routing; test an explicit target and a bound resume from an unrelated checkout with an invalid record.

2. **Resume accepts inconsistent immutable/context metadata** — `prepare-start.ts:74-81`. The target record and selected plan-branch record are checked only for status and target declaration. If their `comparison_base` values disagree, or if the target already contains an execution binding conflicting with the branch's recorded context, preparation succeeds and returns the branch context together with the target record. This mixes distinct provenance while the Start contract requires refusal of inconsistent context and immutable comparison provenance. Compare the immutable comparison baseline and validate any target-side binding when present; target absence of an execution binding is normal. Cover mismatch, missing/present provenance and consistent resume.

3. **Malformed or wrong-identity specs can satisfy approval** — `prepare-start.ts:35-44,100-105`. `specAt` locates the filename but approval checks only `status: approved` in lenient frontmatter; it never validates the spec schema or that the frontmatter ID equals the resolved ID. For example a file named `features/example.md` containing only `status: approved`, or declaring another ID, is accepted as approval of `feature/example`. The current test fixture itself lacks required spec metadata, concealing this. Validate committed spec frontmatter and its identity before accepting approval, with negative tests for malformed and mismatched records.

4. **Orphan target execution binding treated as first start** — `prepare-start.ts:74-84`. If neither plan ref exists but the target's ready PLAN already contains an `execution` binding, preparation ignores it and returns `first: true`; a subsequent binding write could replace existing immutable provenance. Refuse inconsistent orphaned execution context and require recovery instead of preparing a new binding; test a target containing an execution binding with absent plan refs.
