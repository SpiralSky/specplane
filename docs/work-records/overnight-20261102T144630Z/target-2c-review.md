Findings were sent to the coordinator and implementation worker during review.

## Findings

1. **High — newly created worktree is writable without its checkout lease.** `packages/cli/src/plan/first-start.ts:64-66,99-104` acquires checkout leases only for worktrees present before start, then creates a new checkout and runs the arbitrary setup hook there without acquiring its canonical checkout lease. Ordinary writers can acquire a checkout lease without the repository mutation lock (`architecture/reference-cli.md:762-766`), so a concurrent writer can change the new worktree/index/HEAD during setup, or while failed-hook cleanup force-removes it. Retain exclusive coordination for the newly created checkout before invoking setup or deleting it; handle contention without destroying another writer's work and observe the complete ordered-lock contract. Add a deterministic concurrency test where a checkout-only writer attempts to enter while setup is paused, plus failure/preservation assertions.

2. **High — completed claims can strand first start and publication.** `first-start.ts:83-97` commits and optionally pushes the claim before creating the binding. If push fails, or binding/branch creation fails after the claim, the target has `in_progress` but no plan branch. The next call reaches `prepare-start.ts:85-86` and rejects that status as not `ready`, without recognizing the completed claim or resuming pending publication. Reporting the hash does not restore a usable retry. Implement unambiguous claim/phase identification and recovery, preserving target and unrelated changes, and avoid duplicate claims. Exercise actual push rejection against a disposable local remote, and an injected post-claim failure with retry, validating commits, publication, branch provenance and checkout bytes. Ambiguous history must refuse rather than infer authorization. Architecture requires interrupted start/publication recovery (`reference-cli.md:399,413,868`).

3. **Medium — public start receipt and guidance violate the target-aware command contract.** `first-start.ts:108` and `commands/plan.ts:273-287` expose a `claude` launch command and non-null `nextCommand`, omit `comparison_base`, and return `target`, `startBase`, and `freshness` instead of required `target_branch`, `start_base`, and `ref_freshness`. `cli.ts:47` also advertises `--run` execution although it is refused. `reference-cli.md:532` specifies the fields, null compatibility value, and checkout guidance without a host launch command. Test actual human and JSON results, including comparison baseline and dry-run behavior.

4. **Medium — legacy exported start bypasses binding and leases.** `packages/cli/src/plan/flows.ts:125-242` still exports the old start path which creates a default-branch-based implementation branch without the new immutable binding or coordination. No non-test caller was found in this checkout, so this is not an additional CLI entry-point defect today; it is a dangerous exported internal API and existing tests still exercise it. Remove or route it through the new implementation, and repair the flow regression suite to exercise the production path rather than treating old-path results as preservation evidence.

## Evidence limits and follow-up

In particular, current first-start tests exercise a repository-lock collision and direct ref recheck, but not the new-checkout lease race, actual push failure/retry, claim hook failure, stacked marker path, target-plan lease contention, or a ref move within the full start call. Verify these with bounded disposable Git tests; separately verify 2(d)'s dirty reused checkout and missing-checkout preservation. The result is partial implementation evidence, not completion of original step 2.
