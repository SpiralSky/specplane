## Findings

1. **Confirmed: plan-ref movement during commit can produce a false success.** `packages/cli/src/plan/shelve.ts:138` rechecks `report.ref_freshness` before staging, but the post-hook check at lines 145–147 compares only checkout path/branch/bare identity, not captured plan refs or lease ownership. Lines 161–164 may then report success (and, with a remote, publish) although the plan tip became terminal during the commit. Reproduce with `timeout 30s node /tmp/review-shelve-race.mjs` in this workspace: it constructs a disposable repo, creates a valid bound ready branch and a descendant `done` commit, resets to the ready commit, then installs a post-commit hook that advances the branch via `git update-ref`. Observed exit 0 with a successful `shelve` receipt and `branchStatus: status: done`. This violates the precondition to refuse a finish commit awaiting integration and allows publishing a transition based on stale identity. Recheck captured plan and target refs and lease after hooks and before publication; preserve and clearly identify the already-created commit when that check fails. The retry publication path at lines 105–110 also needs a final target/plan/checkout/lease recheck as close to push as practical. A non-cooperating writer can still race the final check; remote lease and exact commit guard remain necessary.

2. **Partial local write failures do not restore operation-owned writes.** After `fs.writeFileSync(file, changed)` at line 134, if writing `indexFile` fails before producing the complete generated bytes (permission/I/O/partial write), the catch at lines 153–155 requires the index output already equal the complete generated string. It reports concurrent edits and leaves the known operation-owned PLAN edit, even when the index remains byte-identical to its captured original. This is a directly identifiable failure phase, not an unavoidable filesystem CAS race. Track each completed write and compare each path with its permitted preimage or owned output; restore only provably owned changes and preserve genuinely ambiguous partial writes. Fault-inject second write failure and verify HEAD/index/PLAN bytes plus error recovery. This was identified by code inspection, not executed.

3. **Prospective index currently uses an obsolete renderer.** `prospectiveIndex` lines 24–34 inventories committed plan files and uses target config, but `generatePlansMd` emits the old table without the required Target column and lacks the specified snapshot API. Therefore transition commits are not compliant with reference-cli § PLANS.md generation even though the temporary tree contains the plan inputs. The transition worker notes this planned seam and the separate plan-index assignment; integration must replace the seam with the actual pure snapshot renderer and verify byte-for-byte regeneration from the resulting HEAD. This is an acknowledged dependency, not a claim that unrelated future plan-index work is complete.

**New confirmed issue: SHA-256 Git commits are truncated after recording.** `shelve.ts` parses successful `git commit` output with `/([0-9a-f]{40})/`, even though `core.abbrev=40` is only a minimum and Git prints 64 hexadecimal digits for a SHA-256 repository. The regex accepts the first 40 digits and then compares them to the full 64-digit ref, so a valid transition commits locally and then reports a final verification error with a nonexistent truncated recovery ID. With a remote it will not publish, and the reported hash is unusable for recovery. Reproduce `timeout 30s node /tmp/review-shelve-sha256.mjs`: disposable `git init --object-format=sha256`, a normal bound plan and no installed commit hook. Observed exit 1, reporting a 40-digit retained ID followed by a distinct 64-digit HEAD. Capture and validate the full object ID according to repository object format; regression should assert successful transition and exact retained hash on publication failure/retry in SHA-256 mode. SHA-1 path was not shown to regress.

The worker's broader tests cover remote movement, custom plan paths and recorded non-default target, simulated PR/dependency status, remote-only plan, ignored/staged inputs and both index failure forms. The pure snapshot renderer and Target column remain an explicit integration obligation for plan-index step 3, not a reason to block unrelated subsequent work. Forged retry commits and final local-ref movement during retry remain unverified. The repair is not ready for unqualified acceptance until the SHA-256 recovery regression is resolved or its support scope is explicitly decided.
