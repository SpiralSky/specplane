## Findings

1. **Started legacy branch can be treated as a new plan.** `packages/cli/src/plan/context.ts:119-124,132-139` checks supplied branch snapshots against independently supplied binding, but a selected snapshot with no binding plus omitted `legacy` falls through to new-plan precedence. For example, a local snapshot `{commit: <full commit>, id}` with `team: "candidate"` selects `candidate` rather than refusing ambiguous historical default. The architecture requires started legacy plans to preserve historical repository-default behavior and refuse ambiguous history; current team config must not retarget them. Make branch existence and selected snapshot determine started/binding/legacy state (or refuse an incomplete state), and require historical-default evidence for an unbound started branch. Add regressions for local-only and remote-only legacy snapshots, missing/changed historical default and preservation. Also reject a supplied binding without a corresponding snapshot when branch discovery is asserted complete.

2. **Fallback default ignores remote-only refs.** `context.ts:53-62` checks only `refs/heads/main` and `refs/heads/master` if `origin/HEAD` is absent. If only `refs/remotes/origin/main` exists, it reports the default unavailable even though `targetTip` explicitly supports remote-only targets and the architecture defines `main`, then `master`, as fallback. Consider local and origin refs for each fallback branch, retaining main-before-master ordering. Test remote-only main, remote-only master and mixed local/remote fallback precedence.

3. **An irrelevant team default can block a started plan.** `context.ts:125` validates all supplied target candidates against the plan's own branch before determining precedence. `plans.target_branch: plan/<id>` is a valid global branch name and `loadConfig` accepts it; if that value is configured after the plan has started on another target, passing it with the existing binding makes resolution fail as an own-branch target even though it is ignored by selection. The contract says the binding selects the target and team-setting changes must not retarget started plans. Apply plan-specific own-target validation only to the selected or otherwise operative target; test bound and legacy plans with this ignored valid setting.

## Coverage and limits

The five tests exercise core precedence, declaration conflicts, explicit legacy evidence, target tip reconciliation, branch-name and binding validation, immutable comparison/start provenance, and selected snapshot divergence. They do not exercise the three scenarios above. The tests cover the resolver as a library rather than lifecycle command flows; later steps must demonstrate authoritative target snapshots, caller-enforced ref rechecks, and end-to-end preservation. The stated prior manual build and focused suite results were not independently rerun.
