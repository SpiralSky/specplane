# Target lifecycle step 4 independent review

Reviewed `c1baa5f427a32aa6dd37cc5a04074936f8cc2cef` against step 04 and `architecture/reference-cli` Finish, Restack, confirmation, and writer coordination contracts. Review is static; no tests or live forge calls were run. Existing worker simulations and test counts are in `target-4-result.md`. Findings below require repair before integration.

1. **High — retry after rebase reuses prior finalization acceptance.** `packages/cli/src/plan/flows.ts:234-237,294-316,322-326`: after a finish commit exists, moving the recorded target and retrying causes the finish commit to be rebased to a new head. Tests are rerun if configured, but `alreadyDone` skips the acceptance challenge entirely; the PR path then pushes that new revision even unattended. A local merge asks only the separate merge decision. The confirmation contract requires fresh finish acceptance after rebase and distinct finalization and merge decisions. Detect a changed reviewed revision and obtain fresh acceptance, with evidence and target bound, before publishing or merging; preserve no-duplicate behavior when the revision truly did not change. Add a retry test for moved target in both PR and local modes including unattended refusal.

2. **High — push is not bound to the captured remote head or reviewed local head.** `flows.ts:301-325`: the code explicitly excludes both plan refs from further rechecks, then uses plain `--force-with-lease`, whose expected SHA comes from the *current* tracking ref. A concurrent ordinary Git fetch can refresh that ref after preparation, enabling a force push over a newly advanced remote branch. Likewise a noncooperating writer or commit hook can move the local plan ref after confirmation, and the command pushes the branch name without verifying that it still names the finalized commit. Use an explicit `--force-with-lease=refs/heads/plan/<id>:<captured SHA>` (including correct absent-ref handling), capture and verify the exact finalized local head and clean state after hooks and immediately before publication, and refuse on unexpected ref movement. Test a tracking-ref refresh and local ref movement between confirmation and push using a disposable bare remote.

3. **High — confirmation rechecks refs but not affected checkout/index bytes.** `flows.ts:239-248,279-281,303-316,338-346`: target checkout cleanliness is checked during readiness, but the async confirmation permits a direct editor or Git process to dirty its working tree/index while target HEAD stays fixed. The finalization check only checks the plan checkout, so it creates the done commit even though the selected target checkout is no longer the reviewed clean state. Similarly a test command can change the target checkout before the review claim; `claimPlan` then commits the working file without a fresh checkout/index check. Recheck the captured target checkout branch, HEAD, index and relevant bytes, plus plan checkout state, immediately before each claim/finalization/merge mutation and after callbacks or hooks. Test target dirty/staged changes during both test execution and finalization confirmation; preserve those edits and refuse before a done or claim commit.

4. **High — partial merge/publication does not reliably resume or report completed phases.** `flows.ts:322-326,346-356,363-376,396-397,648-661`: a successful local merge followed by a failed target push throws the raw Git error before integration evidence or cleanup; retry starts the rebase/merge pipeline again even though target already contains the reviewed plan. A failed review-claim push leaves a local review commit, but retry sees `review` and skips the claim and its publication, so the remote can remain stale; a successful PR push followed by a failed `createPR` similarly throws without naming the pushed head; a failed final-commit hook leaves generated done/archive edits and index entries without a phase-specific recovery report. Restack may successfully rebase and then fail its marker commit, again returning the raw error without recording the rewritten head and missing marker. Inspect and report exact committed/pushed/rebased phases and identities, restore only operation-owned uncommitted finalization changes when safe, and recognize integrated/published results on retry rather than replaying uncertain work. Add deterministic failure tests for local push, PR creation after push, commit hooks, and restack marker failure. Preserve all user edits and never claim rollback after a successful commit or push.

5. **Medium — CLI reports an unfinalized plan as finished.** `packages/cli/src/commands/plan.ts:328-332`, `flows.ts:306-312`: an unattended or declined finalization returns `outcome: ready` before the done commit, but the CLI prints `Finished <id>` with a success exit. This describes a lifecycle transition that did not occur. Distinguish pre-finalization readiness from post-finalization merge readiness and render accurate status for both; test unattended and declined confirmation output.

The manual-done refusal and unchanged-head finalized retry guard are useful, but matching trailers alone do not establish that a revised rebased commit received fresh acceptance. The step's explicit later retarget and shelving implementations were outside this review. Ref selection, original provenance post-rebase checks, matching PR base checks, and ordered lease acquisition were inspected; this review does not certify untested races or full lifecycle coverage.

## Repair review: c2699dec972cac4621aab3fcae498f26aed2e113

**Verdict: further repair required.** Static inspection confirms the repair adds renewed confirmation for finalized retries, explicit remote-SHA force leases and exact publication heads, admin rechecks after confirmations, phase-specific reporting and retry for the covered push failures, guarded restoration on commit-hook failure, and distinct ready output. The worker reports 84 affected tests plus one focused case; I did not rerun them. Two actionable issues remain:

1. **Critical — integrated-target recovery can remove an unrelated checkout.** `packages/cli/src/plan/flows.ts:211-224` enters the target-already-done recovery path before the normal check that the invoking `root` is the checkout of `plan/<id>`. If invoked from any clean linked worktree while recovering a successfully merged plan, `!samePath(root, main)` is true and `dropWorktree(root, false, main)` removes that unrelated worktree. If invoked from a linked target checkout it can remove the target checkout itself. The subsequent branch deletion can fail because the actual plan worktree is still checked out, after the unrelated checkout is already gone. Determine the actual registered checkout of the exact plan branch and verify its identity, branch, clean state, ref and worktree inventory under the leases immediately before cleanup. Never remove the caller's checkout based on path alone. Add recovery tests invoked from an unrelated linked worktree and from a linked target checkout, asserting all unrelated worktrees and files remain intact, plus a successful exact-plan cleanup case.

2. **Medium — renewed finish acceptance omits open gaps.** `flows.ts:337-345` builds the acceptance prompt for an already-finalized retry from criteria alone. A later local merge prompt happens to add open gaps, but that is a separate decision; on the PR path the gaps are never shown in renewed acceptance or publication confirmation. The confirmation contract binds the displayed acceptance report and gaps to the finish decision. Reconstruct current open gaps for the actual rebased revision and include them in the fresh finish-acceptance challenge; assert it for a finalized PR retry with an open gap.

Partial recovery still has a narrower caveat: `finalCommit` snapshots and rollback cover failures from `git commit` only; an earlier failure after writing the status or staging/moving files is reported by the outer catch but requires manual reconciliation.
