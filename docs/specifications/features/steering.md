# Steering and Documentation

Steering is the text Specplane gives an LLM to keep it within the rules: what its role may do, what to do when something is denied, when to ask the user, and how to behave during a plan. Documentation is the text that explains Specplane to people and, in a smaller form, to LLMs. This spec describes both. Steering R51 and R59 are part of the first release (Phase 1 of `docs/release-plan.md`). User-facing and AI-facing documentation (R22, R23) are Phase 2.

The main rule applies to everything in this spec: steering guides an LLM and enforces nothing. What a role may do is decided by its permissions (`roles-and-permissions R50`), which are checked by Specplane whatever the LLM was told. An LLM that ignores steering is still stopped by a denied permission, and an LLM that follows steering can still never do more than its permissions allow (`R59.1`).

## §1 Terms

- **Steering:** instructions given to an LLM about how to use Specplane and what limits apply. It is text, not a rule that Specplane checks.
- **Autogenerated steering:** steering Specplane builds itself from the active roles, permissions, presets and commands, so it stays correct when they change.
- **Custom steering:** steering the user adds or changes (`R59.1`).
- **Soft stop:** the LLM stops a plan run so it can be resumed later (`R27.1`, `plan-execution R27.1`).

## R59: Autogenerated Steering

Specplane generates steering for the LLM and delivers it through the harness (`harness R14` describes how and when instructions are sent). The user does not have to write any for Specplane to work.

- Besides what other sections require, the LLM is told to follow the limits of its role and not to try to get round them (`R59`). This covers asking a different tool, rephrasing an action as a different one, using another role, running a command through a side route, or editing files directly to reach the same result.
- The LLM is told which role it has and what that role may do, in short. Details are looked up on demand (`R23`, `R54`), not repeated in every session.
- For each harness call, command and permission instructions use the same effective role as the permission check, resolved by the LLM role rules from the adapter's identity factors. Steering includes that role's approved custom permissions; changes to the effective role or permissions cause updated instructions to be delivered.
- The LLM is told that Specplane's checks, not steering, decide what is allowed, and that a denial is final for that action.
- Steering is regenerated when roles, presets or permissions change, so what the LLM is told matches what is active. If it cannot be regenerated, the LLM is not left with old text that claims more than the role has; Specplane says so (see `R24`).
- Steering is kept short. Anything that applies only to a command is attached to that command and sent when the command is used (`R14`), not carried in every session.
- Steering never contains secrets. It also tells the LLM to keep private information, such as credentials, out of the summaries it writes into test results (`R61`).

Autogenerated steering covers at least these situations:

- **Specifications.** Before continuing a plan, the LLM checks what changed in each specification the plan references if the plan points at an older commit than the specification's latest commit (`R24`, `plans R28`). An LLM that writes a specification is told it starts as Awaiting Review and that it cannot approve it without the approval permission: allow acts without additional confirmation, request-user waits for acceptance, and deny refuses (`roles-and-permissions R57`).
- **Contradictions.** When specifications at different layers contradict each other, the LLM follows the higher layer and reports the conflict (`specifications R65`). When specifications at the same layer contradict each other, the LLM reports it and does not implement the contradicted behaviour (an assumption beyond the page, which only covers conflicts across layers).
- **Plans.** The LLM works one plan step at a time and records progress, gaps and assumptions in the plan record (`plans R28`).
- **The CLI.** The LLM does not call the Specplane CLI directly, because the CLI is for people and the harness is the LLM's route (`R47`).

### Sending a request, asking the user, or stopping

When an action is not simply allowed, the LLM needs to know which of three things to do. Autogenerated steering says:

- **Permission is request user.** Send a request (`requests R52.3`) naming the one action. Do not do the action first.
- **Permission is deny.** Do not do it and do not look for another way. Tell the user it was refused, and if the user's wishes depend on it, say so and leave the next move to them.
- **The action is one the user runs through a command** (for example approval by a person, `R16`). Ask the user to run the command and say what it will do. Do not try to run it. LLM approval is not this case: when the user asks the LLM to approve, it follows its own `spec.approve` permission mode: allow approves, request user sends a request, deny refuses (`roles-and-permissions R57`).
- **Permission is allow.** Act directly, unless custom steering says to send a request or to ask the user to run a command first (`R59.1`, `R52.3`, `requests R52`). A role with allow that acts directly is not a failure of steering: steering is a guide and does not guarantee the LLM asks first.
- **Blocked in a plan.** When a plan run meets a block, such as a restriction in its environment, the LLM decides whether to go on with work that is not blocked or to soft stop. By default: if useful work within the current step does not depend on the blocked action, send a non-blocking request and continue without skipping an unfinished step; if nothing useful is left to do without the block, or the block affects the whole plan, soft stop. A soft stop is allowed for LLM roles in all default presets (`R27.1`, `plan-execution R27.1`).

### Blocking and non-blocking requests

During a plan run each request is either blocking or non-blocking (`R27.5`, `plan-execution R27.5`), and the LLM chooses. Autogenerated steering tells it:

- Use a **blocking** request when the plan cannot continue correctly without the answer: the next work depends on the action, or going on could build on something the user may refuse.
- Use a **non-blocking** request when the plan can go on without waiting: the request is an improvement, a follow-up, or touches something later steps do not depend on.
- If unsure, the LLM prefers blocking, because the cost of waiting is lower than the cost of building on a refused change. A user can change that default with custom steering (`R59.1`).
- A request outside a plan run has no blocking choice and is simply sent (`requests R52`).

Test T1 (intelligent): read the default steering for each of the five cases above (request user, deny, user-run command, allow, plan block) and the blocking choice, and check that each states what the LLM does and that none claims steering changes a permission.

### Scenarios

- **Given** a role whose approval permission is request user, **when** the LLM wants a specification approved, **then** it sends a request and does not approve.
- **Given** a role with allow for approval, **when** the user said "approve the spec", **then** the LLM may approve without asking again, and the user documentation warns that steering does not guarantee it asks first (`R22`).
- **Given** a plan run where part of the current step needs a tool the environment forbids, **when** the LLM reaches it, **then** by default it sends a non-blocking request and either continues independent work within that step or stops the plan with a soft stop; it never skips the unfinished step.
- **Given** a plan that references a specification changed since the plan was written, **when** the run continues, **then** the LLM is told to check what changed first.

## R59.1: Custom Steering

The user can customise steering overall and per command or permission (`R59.1`). Customisation is for how an LLM should behave inside what it is allowed to do; it cannot widen or narrow a permission.

- **Overall steering** applies to all LLM roles and all commands. **Per-command** and **per-permission** steering applies only when that command is used or that permission is the one in question. A more specific custom steering is applied together with the general one; on a direct conflict between them, the more specific wins.
- Typical uses: when to send a request (only when the user asked for the change, or whenever the LLM sees a possible improvement), whether the LLM asks the user to run a command even where it could act, how cautious to be with blocking requests, and project conventions.
- Custom steering is changed through configuration (`configuration R25`) and is shared with the project like other configuration (`roles-and-permissions R50` lists who may change configuration). A change to it is a configuration change like any other.
- Custom steering is added to the autogenerated steering; it does not remove the rule not to bypass limits (`R59`) or the permission steering (`R51`). If custom steering tells the LLM to do something its permission denies, the permission still decides, and the LLM is expected to say so rather than try.
- The user can see the complete steering an LLM receives for a command or permission, autogenerated and custom together, so there are no hidden instructions (`R54`).

Test T1 (deterministic): with a custom steering value set for one command, the steering shown for that command contains both the autogenerated text and the custom text, and the steering for another command contains only the autogenerated text.

## R51: Permission Steering

Every permission has instructions attached to it that tell the LLM two things (`R51`):

1. **The limit.** What this permission allows and what it does not, in the mode the LLM's role has for it (allow, request user or deny).
2. **No bypass.** An explicit statement that the LLM must not attempt to get round the permission when it is denied or limited.

These instructions are shown in three places:

- Up front, in short, as part of the steering for the LLM's role (`R59`).
- When the LLM uses the command the permission controls, with the instructions for that permission (`R14`, `harness R14`).
- When the permission refuses an action: the reply names the permission, says the action was refused or needs a request, tells the LLM not to look for another way, and, when the mode is request user, says to send a request (`requests R52`, `roles-and-permissions R50`).

The instructions are also part of the permission documentation, which people read through the CLI and the harness (`R54`). When a permission is added, every default preset has steering for it before it is shipped; a permission with no attached instructions is reported as a warning (`R24`).

Scenarios:

- **Given** a role denied spec editing, **when** the LLM is asked to edit a spec, **then** it says the permission denies it, does not edit the file by any other route, and does not propose an alternative that has the same effect.
- **Given** a role with request user for spec editing, **when** the LLM wants the edit, **then** it sends a request rather than editing, and waits as the plan or the user directs.

Test T1 (deterministic): for every permission kind in the default presets, the generated instructions are non-empty and include the no-bypass statement.

## R22: User-facing documentation

Phase 2 of the first release. The user-facing documentation describes what every feature does, including specification formats, configuration and commands (`R22`).

- It covers the concepts (layers, specifications, plans, roles, permissions, requests, steering), every command with its permissions, every configuration key with its default and effect, and the specification formats.
- It is available in the repository's docs and from the CLI, and the harness can read the same text (`R23`).
- It lists what each supported harness supports (`R35.1`) and states plainly where a harness lacks something.
- Notes it must include, because other requirements call for them: group approval and how the command warns and lists the specs approved together (`R16`); that an LLM role with allow for spec approval approves without confirmation and that steering does not guarantee it asks first (`R59.1`, `roles-and-permissions R57`); that audit retention has a stated default and can be configured (`R13.1`); that storing logs in git may expose private information and is not removed by retention (`R61.4`).

Test T1 (intelligent): list the commands and configuration keys that exist, and check that each appears in the user documentation with its default and effect.

## R23: AI-facing documentation

Phase 2 of the first release. The AI-facing documentation is derived from the user-facing documentation (`R23`), so it cannot disagree with it and is not maintained separately.

- **Essentials are loaded into context:** the orientation, the LLM's role and limits, and the steering for the commands in use. This is kept small.
- **Everything else is searched on demand.** The LLM is told that more documentation exists and how to look it up, and is required to search it, not guess, when it needs information it does not have (`R23`).
- When the user-facing documentation changes, the AI-facing documentation reflects it by being generated again, not edited by hand.
- Instructions already in context are not sent again, and are sent again if Specplane cannot tell or the context was compacted (`R14`).

Test T1 (deterministic): generating the AI-facing documentation from the user-facing documentation twice gives the same result, and the always-loaded part is smaller than a stated limit.

## §2 Edge cases

- **Steering and permission disagree.** The permission wins. The LLM is told to report the disagreement, and Specplane warns (`R24`).
- **LLM ignores steering.** Nothing in Specplane relies on it. A denied action is refused and a request-user action cannot be done without acceptance (`roles-and-permissions R50`).
- **Harness cannot deliver steering at the right time.** Specplane delivers it at the nearest earlier point, for example at the start of the session, and says so; it does not pretend steering was delivered (`R35.1`).
- **User-run commands.** Steering can ask the user to run a command, but cannot run it for the user, and the LLM has no access to the CLI (`R47`).
